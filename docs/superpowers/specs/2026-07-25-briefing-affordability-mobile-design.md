# 설계 — 브리핑 · 정확한 자금 · 모바일 레이아웃 (2026-07-25)

## 1. 배경과 문제

현재 앱은 **탐색은 되지만 판단을 돕지 않는다.** 사용자가 "이걸 어떻게 활용해야 하나" 싶은
근본 원인이 여기에 있다.

사용자 상황(확인됨): **당장 매수 계획은 없고 관망·감각 유지**. 다만 나중에 첫 매수든
갈아타기든 실제로 쓸 때를 대비해 **세 경우 모두에 공통으로 쓰이는 기반**부터 정확히 하고 싶다.

따라서 목표는 둘이다.

1. **매일 5분 — "지난번 이후 뭐가 바뀌었나"를 알고 닫는다.** 지금 앱엔 이 축이 통째로 없다.
2. **숫자가 맞다.** 관망 중에 본 숫자가 나중에 실제 결정에 그대로 쓰일 수 있어야 한다.

## 2. 범위

A → C → B → D 순으로 전부 진행. 각 단계 종료 시 `npx next build` + 동작 확인 후 다음 단계.
A가 C의 재료이므로 순서는 고정이다.

**범위 밖(명시적 제외)**

- **통근 시간 축**: 집 선택의 1순위 축이지만 카카오 길찾기(모빌리티) API가 별도 신청·쿼터
  제약이 있고, 직선거리 근사는 수도권에서 오해가 크다(강 건너·산 너머). 별도 건으로 분리.
- **푸시 알림**: 웹앱이라 신뢰성 있는 푸시가 어렵다. "열었을 때 diff를 보여주는" 방식으로 대체.
- **전월세 데이터**: 현재 매매 전용. 유지.

## 3. 구현

### A. 자금 계산 정확도

#### A-1. 부대비용을 필요자금에 반영

**설계 원칙: `requiredCash` 한 곳만 고친다.** 마커 색칠·리스트 여유 배지·평형 카드·
`bestGap()`이 전부 이 값을 공유하므로 자동 전파된다. `assets`가 갈아타기 매도대금을
흡수한 것과 같은 패턴.

`app/lib/loanPolicy.js`에 새 순수 함수 `calcAcquisitionCost()`를 추가한다.
`loanPolicy.js`는 supabase 미의존이므로 `scripts/*.mjs` 단독 검증이 가능하다 — 유지할 것.

```js
calcAcquisitionCost({ price, area, householdType, isFirstTime, regulated })
  → { acquisitionTax, localEduTax, ruralTax, brokerFee, registryEtc, total, rate }
```

**취득세** — 지방세법 §11①8 (주택 유상거래)

| 취득가액 | 세율 |
|---|---|
| 6억 이하 | 1.0% |
| 6억 초과 ~ 9억 이하 | `(가액 × 2 / 3억 − 3)` % — 소수점 5째 자리 반올림, 1~3% 선형 |
| 9억 초과 | 3.0% |

중과 — 지방세법 §13조의2:
- 조정대상지역(= 본 앱의 `isRegulated`) 2주택 8%, 3주택 이상 12%
- 비조정 3주택 8%, 4주택 이상 12% (2주택은 일반세율)
- **결정(2026-07-25, 사용자 확인): `다주택` = 2주택 취득으로 간주**해 조정 8% /
  비조정 일반세율을 적용한다. 3주택 이상 구분을 위한 주택 수 입력 필드는 **추가하지 않는다** —
  사용자 본인이 무주택 또는 최대 1주택이라 3주택 이상 경로는 실제로 밟히지 않는다.
  `다주택` 선택 시 "3주택 이상은 실제 세율이 더 높습니다(12%)" 한 줄 주석만 표시해
  나중에 상황이 바뀌면 알아챌 수 있게 한다.

**지방교육세** — 지방세법 §151①1나: 주택 유상거래는 `취득세율 × 10%` (0.1~0.3%).
중과세율(8%/12%) 적용 시에는 **0.4% 고정**.

**농어촌특별세** — 농특세법 §5: **전용면적 85㎡ 초과분만** 0.2% (85㎡ 이하 비과세).
중과 시 8%→0.6%, 12%→1.0%. `area`(전용 ㎡)를 인자로 받는 이유가 이것이다.

**생애최초 감면** — 지방세특례제한법 §36조의3: 실거래가 12억 이하 주택,
**취득세 200만원 한도 감면** (2022-06-21 이후 취득분, 소득·주택가격 요건 폐지).
`isFirstTime`이 true이고 `price ≤ 120000`(만원)이면 취득세에서 최대 200만원 차감.

**중개보수** — 공인중개사법 시행규칙 별표1 (2021-10-19 시행), 주택 매매·교환:

| 거래금액 | 상한요율 | 한도액 |
|---|---|---|
| 5천만 미만 | 0.6% | 25만원 |
| 5천만 ~ 2억 미만 | 0.5% | 80만원 |
| 2억 ~ 9억 미만 | 0.4% | — |
| 9억 ~ 12억 미만 | 0.5% | — |
| 12억 ~ 15억 미만 | 0.6% | — |
| 15억 이상 | 0.7% | — |

상한요율이며 실제는 협의로 정한다 → **상한 적용을 가정**하고, VAT 10%를 더한다(일반과세자 기준).
보수적(비싸게) 추정하는 쪽이 "살 수 있다고 했는데 못 사는" 실패보다 낫다.

**등기·기타** — 법무사 보수 + 국민주택채권 매입 후 할인손실 + 증지.
채권 할인손실이 시가표준액·채권 시세에 따라 변동해 정확한 계산이 불가능하므로 근사한다:
`price × 0.15% + 40만원`. 9억이면 약 175만원. 주석에 근사임을 명시.

이 두 계수는 **`REGISTRY_RATE` / `REGISTRY_FIXED` 명명 상수로 파일 상단에 노출**한다.
실제 견적을 겪은 뒤 숫자만 갈아끼울 수 있어야 하고, 다른 항목(법정 세율)과 달리
**근거가 법령이 아니라 경험치**라는 점이 코드에서 구분돼 보여야 한다.

**`calcMaxLoan` 변경**

```js
requiredCash = max(0, price − maxLoan) + acquisitionCost.total
```

반환값에 `acquisitionCost` 객체를 함께 실어 UI가 내역을 펼칠 수 있게 한다.
`affordable` 필드는 의미가 모호하고 현재 UI에서 미사용이므로 이번 기회에 제거한다.

**호출부 변경** — `KakaoMap.js`의 `loanForPrice(price)`에 `area`가 필요해진다
(농특세 85㎡ 판정). 시그니처를 `loanForPrice(price, m2)`로 바꾸고:
- 평형 카드: `g.m2` 전달 (정확)
- `bestGap()`: 각 평형 그룹의 `g.m2` 전달 (정확 — 이미 그룹 순회 중)

즉 두 호출부 모두 실제 전용면적을 알고 있으므로 근사가 필요 없다.

#### A-2. 월 상환액

`calcMaxLoan` 반환값에 추가:

```js
neededLoan       // 실제로 빌릴 금액 = min(maxLoan, max(0, price + 부대비용 − assets))
monthlyPayment   // neededLoan 기준, 실제 금리 월 원리금 (사용자가 실제로 내는 돈)
dsrRatio         // neededLoan 기준, 스트레스 금리 연상환액 / 연소득 (규제 심사 수치)
```

**`maxLoan`이 아니라 `neededLoan` 기준으로 계산한다.** 자기자금이 많으면 한도까지 빌릴
이유가 없으므로, 한도 기준 월납은 실제와 동떨어진 숫자가 된다. 따라서 `calcMaxLoan`은
`assets`를 새 인자로 받는다(기본 0 → 미설정 시 `neededLoan = maxLoan`, 즉 최대로 빌렸을 때).

이 정의는 기존 `gap` 판정과 **정확히 일치한다**:
`gap ≥ 0` ⟺ `assets ≥ price + 비용 − maxLoan` ⟺ `maxLoan ≥ neededLoan`.
즉 구매 가능 판정이 두 갈래로 갈리지 않는다.

**금리를 두 개 쓰는 이유를 반드시 UI에 드러낸다.** `monthlyPayment`는 실제 금리(`rate`)로
계산한 실제 지출이고, `dsrRatio`는 스트레스 금리(`rate + stressRate()`)로 계산한 규제 수치다.
둘이 다른 게 정상이며, 이를 설명하지 않으면 사용자가 계산 오류로 오해한다.
`HelpModal.js`에 한 단락 추가.

`annualPaymentPerUnit()`이 이미 있으므로 계산은 재사용:
`monthlyPayment = neededLoan × annualPaymentPerUnit(rate, termYears) / 12`

#### A-3. UI 반영

평형 카드(`KakaoMap.js` 평형별 시세·대출 섹션):

```
84㎡ · 25평                        [보유 지정] [12건 · 🏠 매물]
평균 9.6억 · 최근 9.8억

대출 6.0억 [LTV]              필요자금 3.35억
월 284만원 · DSR 38%          ▸ 부대비용 3,500만 내역

✓ 매수 가능 · 여유 1,200만
```

`▸ 부대비용 내역`은 접힌 상태가 기본이고, 펼치면 취득세/지방교육세/농특세/중개보수/등기 각 줄.
평형 카드가 이미 추세 차트 인라인 선택기 역할을 하므로, 내역 토글은 카드 클릭과 충돌하지
않도록 `e.stopPropagation()` 처리한다(`naverLandLink`·`ownedBtn`과 동일 패턴).

**마이그레이션 주의**: 부대비용이 들어가면 기존에 🟢이던 핀 일부가 🔴로 바뀐다. 사용자가
"앱이 고장났나" 싶지 않도록, 자금 프로필이 설정된 상태에서 최초 1회 컨트롤 패널에 안내
배너를 띄운다(localStorage 플래그로 1회만). 문구: "필요자금에 취득세·중개보수 등
부대비용이 반영되도록 개선했습니다. 이전보다 필요자금이 늘어 보입니다."

### C. 지도 — 내 상황 축 늘리기

A가 끝나면 두 축이 거의 공짜로 붙는다.

#### C-1. 월 상환액 필터

기존 `PRICE_FILTERS` 옆에 월 상환 상한 필터를 추가한다. 사람이 감당 여부를 판단하는
실제 단위가 "월 얼마"이기 때문에 가격 구간보다 직관적이다.

```js
const MONTHLY_FILTERS = [
  { value: "all", label: "월상환 무관", max: Infinity },
  { value: "m100", label: "월 100만원 이하", max: 100 },
  { value: "m150", label: "월 150만원 이하", max: 150 },
  { value: "m200", label: "월 200만원 이하", max: 200 },
  { value: "m300", label: "월 300만원 이하", max: 300 },
];
```

- **자금 프로필(연소득)이 설정된 경우에만 노출** — 대출 계산이 불가능하면 의미가 없다.
  `hasProfile` 조건은 이미 `SORT_GAP`·`onlyBuyable`에서 쓰는 패턴이다.
- 판정: 단지의 어느 평형이든 `gap ≥ 0`이고 그 평형의 `monthlyPayment ≤ max`이면 통과.
  **같은 평형에서 두 조건이 동시에 성립**해야 한다 — A평형은 여유가 있고 B평형은 월납이
  싸다고 통과시키면 실제로 살 수 없는 단지가 통과한다.
  `bestGap()`과 같은 순회에서 계산되므로 `bestGap()`을 `bestFit()`으로 확장해
  `{ gap, monthly }`를 함께 반환한다(월납 조건을 만족하는 평형 중 여유 최대).
  **마커·리스트가 같은 함수를 공유하는 현 구조를 유지**할 것.
- ⚠️ `renderMarkers`를 부르는 `useEffect` deps에 새 상태 `monthly`를 **반드시 추가**한다
  (CLAUDE.md의 마커 함정 항목). deps에 빠지면 필터가 마커에 반영되지 않는다.

#### C-2. "얼마 더 모으면 되나"

지금 리스트 배지는 `부족 3,200만`에서 끝난다. 이를 행동 가능한 문장으로 바꾼다.

자금 프로필에 **월 저축액** 필드(`monthlySaving`, 만원)를 추가하고, 값이 있으면:

```
부족 3,200만 · 월 200만 저축 시 약 16개월
```

- 계산은 단순 나눗셈(`Math.ceil(부족액 / 월저축)`). 집값 상승·금리 변동은 반영하지 않는다 —
  가정을 늘리면 오히려 신뢰도가 떨어진다. 툴팁에 "현재 시세 기준 단순 계산" 명시.
- 월 저축액 미입력 시 기존 `부족 3,200만` 그대로. 새 필드 강요하지 않음.
- 표시 위치: 세부패널 평형 카드(공간 여유 있음). 리스트 배지는 좁으므로 기존 유지.

### B. 뉴스탭 → 오늘의 브리핑

`/news` 상단에 브리핑 블록을 얹는다. 기존 칩 필터 + 날짜별 뉴스 목록은 그 아래 그대로 유지.
지도는 "탐색할 때 들어가는 곳"으로 역할이 깔끔하게 나뉜다.

#### B-1. `/api/briefing` (신규)

즐겨찾기 단지의 최근 실거래를 모아 돌려준다.

**핵심: 새 외부 API 호출이 0이다.** `/api/cron/refresh`가 이미 매일 06:00에 즐겨찾기 지역
최근 2개월을 재수집해 `trade_raw_cache`에 넣어두므로, 이 라우트는 캐시만 읽는다.
`trades.js`의 `fetchRawMonths`를 재사용하되 미스가 나도 국토부를 때리지 않도록
**캐시 전용 모드**가 필요하다 — `fetchRawMonths(codes, { cacheOnly: true })` 옵션을 추가한다.

```
GET /api/briefing
→ {
    complexes: [{
      lawdCd, umdNm, aptNm,
      recent: [{ area, amount, dealDate }],   // 최근 30일 거래, 최신순
      prevAmount,                              // 같은 평형 직전 거래가 (변동률 계산용)
    }],
    upcoming: [{ aptNm, kind: "lease"|"note", label, dday }],  // D-30 이내
  }
```

- `upcoming`은 `favorites`의 `lease_end`/`note_date`에서 파생. 0004 마이그레이션 미적용
  환경에서는 컬럼이 없으므로 **`/api/favorites` GET의 기존 폴백 패턴을 따라** 빈 배열로 graceful.
- 즐겨찾기가 0개면 빈 응답 + 안내 문구(지도에서 ★을 눌러 담으라고).

- **`🆕` 판정**: localStorage에 단지별 마지막 확인 거래일(`re_briefing_seen` = `{key: dealDate}`)을

- **💰 카드**: `classifyNews()`가 이미 카테고리를 내므로 `대출·금리`·`정책·세금`만 필터.
  `keyword`가 관심지역(` 아파트` 접미)인 기사는 ⭐로 함께 상단에. 신규 분류 로직 불필요.
- 브리핑 카드는 **데이터가 있을 때만 렌더**한다. 즐겨찾기 0개인 신규 사용자에게 빈 카드 3개를
  보여주면 오히려 혼란스럽다 — 대신 "지도에서 ★로 관심 단지를 담으면 여기 변동이 뜹니다" 한 줄.

#### B-3. 지도 → 브리핑 진입점

현재 컨트롤 패널의 `📰 뉴스` 링크에 **미확인 변동 개수 배지**를 붙인다(`📰 뉴스 3`).

지도 마운트 후 `/api/briefing`을 **비차단으로 한 번** 호출해(캐시 전용이라 가볍다)
`re_briefing_seen`과 비교, 개수만 계산한다. 실패하면 배지만 생략하고 지도는 정상 동작한다.
지도 초기 로드를 지연시키지 않도록 실거래 로드 완료 후에 호출할 것.

### D. 모바일 레이아웃 재구성

### 문제 원인

- 상단 `controlPanel`(`z:10`)이 세로 flex로 **무한정 자란다**. 즐겨찾기/자금 드로어를 열면
  화면 절반을 넘긴다. 모바일 스타일에 `maxHeight`가 없다(`KakaoMap.js:781`).
- 하단 `detailPanel`(모바일 시트, `maxHeight:60vh`, `z:10`) — 상단과 **z-index가 동일**해
  DOM 순서로만 겹쳐 그려진다.
- `mobileListSheet`(`62vh`, `z:12`)도 같은 문제.

즉 상·하단 합이 100vh를 쉽게 넘는데 서로를 모른다.

### 해결: 상단 1줄 고정 + 모든 패널을 하단 시트 하나로

```
┌───────────────────┐
│ 동안구 · 312건  ⚙️ 📰 │  ← 1줄 고정 (항상 이 높이)
├───────────────────┤
│                    │
│       지  도       │  ← 넓게 확보
│                    │
├───────────────────┤
│ ━━  평촌더샵     × │  ← 하단 시트, 한 번에 하나만
│ 9.8억 · 84㎡       │
└───────────────────┘
```

**구조**

1. **상단 바** (모바일 전용, 고정 높이 1줄): `지역명 · 상태 요약` + `⚙️`(설정 시트 열기) + `📰`(뉴스).
   지역 select·면적/가격/월상환 필터·즐겨찾기·자금은 전부 ⚙️ 시트로 이동.
   현재 `status` 문자열은 필터 태그·구매가능 수까지 붙어 한 줄에 안 들어간다 →
   모바일 상단 바에는 **짧은 형태**(`지역명 · 거래 N건`)를 따로 만들고 `whiteSpace:nowrap` +
   `textOverflow:ellipsis`로 잠근다. 전체 상태 문자열은 ⚙️ 시트 안에 그대로 표시.
   필터가 걸려 있으면 `⚙️`에 점 표시(●)를 붙여 "지금 필터 켜짐"을 1줄에서도 알 수 있게 한다.
2. **하단 시트 슬롯 하나** — `mobileSheet` 상태를 단일 값으로 관리:
   `null | "settings" | "list" | "detail"`. 동시에 둘 이상 열릴 수 없다 → **겹침이 구조적으로 불가능**.
   - 단지 선택(`setSelected`) 시 자동으로 `"detail"`
   - 목록 행 클릭 시 `"detail"`로 전환 (기존 `selectComplex`의 `setShowList(false)`가 이 규칙의 前身)
   - `showFavs`/`showProfile`은 모바일에서 `"settings"` 시트 내부 탭으로 흡수
3. **z-index 정리** (`mapStyles.js`에 상수화):
   `MAP=0` / `TOPBAR=20` / `SHEET_BACKDROP=30` / `SHEET=31` / `MODAL=50`(기존 `modalOverlay` 유지)
4. 시트 높이는 `maxHeight: 70vh`, 내부 스크롤. 상단 바가 1줄이라 70vh를 써도 지도가 보인다.
5. 시트 뒤에 반투명 백드롭 — 탭하면 닫힘. 기존 `closeBtn`(×)도 유지.

**데스크톱은 변경 없음.** 좌측 패널이 컨트롤+리스트로 전체 높이를 쓰는 현 구조가 잘 동작하고
있으므로 건드리지 않는다. 분기는 기존 `isMobile`(matchMedia 640px) + 인라인 스타일 스프레드
패턴을 그대로 따른다.

**리팩토링 (범위 내)**: `KakaoMap.js`가 이미 1,279줄이고 이 작업으로 더 늘어난다.
모바일 상단 바와 시트 셸을 `components/MobileShell.js`로 분리한다. `listContent`처럼
이미 JSX 조각이 변수로 빠져 있으므로 자연스럽게 이어진다. 세부패널 본문·리스트 본문은
그대로 두고 **껍데기만** 분리해 변경 범위를 좁힌다.
